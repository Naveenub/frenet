# Architecture (Phase 1)

**Stack.** Backend: Node.js >= 22.13, strict TypeScript (ESM), js-libp2p, `node:sqlite`. Frontend (`web/`): plain JavaScript ES modules, no framework, bundler or build step. This deliberately differs from the original spec (Next.js/React/TypeScript/Tailwind frontend, Go or Rust backend); see the README "Stack (as built)" table. The only Rust is inside the `@chainsafe/libp2p-quic` dependency.

## Messaging protocol `/frenet/msg/1.0.0`
- One stream per message: `{v:2,id,ts,to,body,sig}` JSON, closed by sender. `sig` is Ed25519 (base64) over `frenet-msg/v2\nfrom\nto\nid\nts\nbody`, so it binds sender, recipient, id and timestamp, not just the body.
- Sender identity = `connection.remotePeer` (authenticated by Noise). Claimed identity is never read from the payload.
- Receiver checks: size <= 32 KB frame / 16 KB body, schema, timestamp within 5 min, unseen `(peer,id)`, token-bucket rate limit (burst 20, 2/s).
- Signed per message: the sender is `remotePeer` and the signature must verify under that peer's key (the public key is embedded in the Ed25519 peer ID) and name us as `to`. Unsigned (v1), wrong-recipient and bad-signature messages are dropped. Signature, sender and recipient are stored, so any third party can re-verify a stored message with `verifyMessage()`. Limits: no forwarding yet (signer must equal the connection peer); signing proves authorship and recipient, not that the recipient read it; no sender-deniability; old unsigned v1 nodes can no longer message this version.

## Blocks `/frenet/block/1.0.0`
`put(bytes)` -> sha256 raw CIDv1, stored in SQLite, announced via DHT `provide`. `get(cid)` -> local, else `findProviders`, request the CID, verify sha256 before caching, then re-announce (replication). Cap 1 MB/block. Raw blocks are plaintext to anyone with the CID.
**Re-announcement.** A provider record lives 48 h on the DHT peers that hold it (kad-dht `PROVIDERS_VALIDITY`). kad-dht's own re-provider refreshes only the records it knows about, and it keeps them in the libp2p datastore, which is in memory unless one is supplied, so a restart forgot every block we ever announced and the content became unfindable although it was still in SQLite. `Blocks.reannounce()` lists every unexpired block in the store (ids only; pinned own blocks first, then replicas), skips blocked CIDs, and announces them with 8 in flight. It runs `reannounceDelayMs` (30 s, so peers have been found) after start and then every `reannounceMs` (12 h, a quarter of the validity; `--reannounce-hours`, 0 = off). If a run could not announce anything (no peers yet) it retries after 5 min instead of waiting a full interval. `lastReannounce` is shown in `/api/status`; `POST /api/operator/reannounce` runs it by hand. **Limits.** It only keeps content findable while some node holds it: expired replicas and deleted blocks are gone. The cost is one DHT `provide` per block per run, so a node holding very many tiny blocks spends a long time per run (runs never overlap). The in-memory provider records of deleted or expired blocks are not withdrawn until restart (blocked content is: see Content safety).

## Files (`src/files.ts`)
File -> 256 KB chunks -> each sealed with AES-256-GCM (random per-file key, random 96-bit nonce, AAD `c<index>`) -> blocks. Manifest `{name,size,chunks[]}` is sealed too (AAD `m`) and its CID is the file ID. Link: `frenet://<manifestCid>#<key>`; the key is never stored or sent by the node, so providers see ciphertext only. `{encrypt:false}` makes a public file. Max 16 MB. No key recovery: lose the link, lose the file.

## Sites (`src/sites.ts`, `src/gateway.ts`)
A site = public files (Files with `encrypt:false`) plus a manifest block `{v:1,type:'site',index,files:{path->fileCid}}`; the site ID is the manifest's CID. Paths are relative, `[A-Za-z0-9._-]` segments, no `.`/`..`; max 64 files / 32 MB. The manifest is validated on read because the publisher is untrusted (path charset, CID shape, prototype keys are not files).
The gateway (default `127.0.0.1:7778`) serves `GET/HEAD http://<siteCid>.localhost:<port>/<path>`: the `Host` must be a valid site CID (DNS-rebinding defence; each site is a separate browser origin). Responses carry `default-src 'none'; img/style/script/font/media/connect 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`, `nosniff`, `no-referrer`, CORP same-origin. Only a fixed MIME allow-list is rendered; other types are served as attachments. Browser subresource requests from other pages (`Sec-Fetch-Dest` other than `document`, unless same-origin) are refused so a web page cannot make this node fetch arbitrary CIDs. Clients that send no `Sec-Fetch-*` headers (curl) are allowed: they are already local.
Limits: static content only; the gateway is plain HTTP on loopback; fetching an unseen site reveals the CID you want to your DHT neighbours. Mutable addressing and search live in the next section.

**Scope.** The gateway serves FRENET sites only. It does not proxy the public web, so there is no HTTPS browsing, tracker blocking or permission manager; these are not in the spec's feature list. The CSP and `Permissions-Policy` above harden published sites and are not a user-facing permission system.

## Names, updates and search (`src/names.ts`)
**Record.** `{v:1,name,pub,target,seq,ts,keywords[],title,sig}`. `pub` is the publisher's raw Ed25519 public key (base32, 52 chars) and is part of the name (`<name>.<pub>`), so names are self-certifying: `sig` is Ed25519 over `frenet-name/v1\nname\npub\ntarget\nseq\nts\nkeywords\ntitle` and must verify under `pub`. There is no registry to capture; a different key is simply a different name. Validation (`validateRecord`) checks the label (`[a-z0-9-]`, 1-63), `pub` round-trips as a 32-byte key, `target` is a canonical CID, `seq` is a positive safe integer, `ts` is not more than 5 min in the future, <= 8 keywords of `[a-z0-9]{2,32}` (no duplicates), title <= 80 chars without control characters, and the signature. Anything else is dropped.
**Updates.** `publish(name, target)` signs `seq = max(local, network) + 1`. Stores and resolvers keep only the highest `seq` per `(name, pub)` (`Store.putName`), so a stale valid record cannot roll a name back locally. The site manifest a name points at is an ordinary immutable site, so every version keeps its own `frenet-site://` ID.
**Distribution.** No DHT value store: like blocks, a record is announced as a provider record, under `sha256("frenet-name/v1\nname\npub")` for resolution and `sha256("frenet-kw/v1\nword")` per keyword for search. Peers holding a record serve it over `/frenet/name/1.0.0` (one JSON request <= 512 B, response <= 64 KB, rate limited like blocks): `{k:'name',name,pub}` -> record or null, `{k:'kw',word}` -> up to 20 records. `resolve` asks up to 8 providers, verifies each answer and takes the highest `seq` (15 s in-memory cache; falls back to the locally cached copy if the network has nothing). Every foreign record is stored (capped at 5000, oldest first) so this node can serve it onward. Own names are re-announced every 6 h.
**Search.** `search(q)` tokenises to <= 5 words, asks keyword providers per word, keeps only records that verify and really contain that word (a provider cannot stuff records into a keyword it does not carry), then returns the records whose name/title/keywords contain *all* words: own first, then newest.
**Gateway.** Host `<name>.<pub>.localhost` is resolved to the current `target` and served exactly like a site (same CSP, own origin per name). Resolution happens only after the method and `Sec-Fetch-*` checks, so a drive-by page cannot make this node run name lookups.
**Local API.** `POST /api/sites` also takes `name`, `title`, `keywords` (validated before anything is published, so a bad name leaves no orphan site); `GET /api/names`, `GET /api/names/resolve?name&pub`, `GET /api/search?q`.
**Limits.** Names are not globally human-memorable (the key is in the address). Rollback to an older valid record is possible if only stale holders are reachable. Search is opt-in, unranked and spammable: anyone can publish under any keyword; results are not ranked by reputation, and there is no content (full-text) index. Provider records expire; own names are re-announced every 6 h, and so are blocks (see Blocks), but only the publisher announces a name: nodes that resolved it keep the signed record and serve it to anyone who asks, yet nobody finds them without a provider record, so a name (and keyword search) still needs its publisher online while the site's blocks can live on in replicas. No transfer or revocation of a name.

## Voice and video (`src/calls.ts`, dashboard)
WebRTC media is browser to browser (DTLS-SRTP); the node only relays signalling. `/frenet/call/1.0.0`, one JSON signal per stream: `{v:1,id,call,to,kind,ts,data,sig}`, `kind` one of `offer|answer|ice|hangup|decline`, `data` <= 16 KB (SDP or ICE as a JSON string). `sig` is Ed25519 over `frenet-call/v1\nfrom\nto\ncall\nkind\nid\nts\ndata`; `from` is `remotePeer`, never a claimed field. The receiver checks frame size, schema, recipient, signature, 5 min window, unseen `(peer,id)`, a per-peer rate limit (burst 60, 20/s) and an extra offer limit (burst 3, one per 5 s) so a peer cannot ring you in a loop. Signals are not stored.
The dashboard never touches the camera or microphone until you press Call or Accept. Only the peer that started a call can answer, hang up or decline it (matched on call id and authenticated peer); offers while busy are declined. It sends one offer and one answer with all ICE candidates gathered (max 4 s wait), so no trickle race; `ice` is accepted for other clients.
**Limits.** A direct call reveals your network address to the other side. No STUN/TURN is configured by default, so calls work on a LAN or between publicly reachable hosts; `--ice-server stun:HOST[:PORT]` adds STUN (that server then learns your address). No TURN or relayed media, so symmetric NAT/CGNAT pairs can fail. No group calls. Signalling proves who sent a signal, not that the media endpoint is that person: compare out of band for high-stakes calls. Real browser media was not tested here (see README).

## Communities, group chat and governance (`src/groups.ts`)
**Model.** A community has a random 64-bit id, a name and an owner (its creator). Only the owner signs rosters: `{name,seq,members[]}` (<= 100 peer IDs, owner included). Anything else (messages, proposals, ballots) is signed by the member who made it. Wire: `{v:1,community,kind,id,ts,body,sig}`, `kind` one of `roster|msg|proposal|vote`, `sig` over `frenet-group/v1\nauthor\ncommunity\nkind\nid\nts\nbody`, author = `remotePeer`. One signature covers all recipients, so stored events stay verifiable by third parties. The sender fans each event out to every member it can reach (8 s dial limit; unreachable members are reported, nothing is queued).
**Membership.** An inbound roster for an unknown community creates an *invitation* only: nothing is accepted from that community until you press Join, at most 50 invitations are held, and Leave is sticky so an owner cannot re-invite you. A roster is accepted only from the recorded owner, with a higher `seq`, and must contain the owner. Removed members receive the roster and move to "removed". Events from non-members, or for communities you have not joined, are dropped.
**Chat.** Body <= 4 KB, same replay, skew and rate-limit checks as messaging (burst 60, 10/s per peer).
**Governance.** A proposal `{title<=80,text<=2000,closes}` (voting period 1 min to 30 days) freezes the roster as its electorate when first seen. A ballot `{proposal,choice: yes|no|abstain}` counts only from an electorate member, before `closes`. `tally()` keeps each member's latest ballot, requires strictly more than half the electorate to cast any ballot (quorum), and passes if yes > no (a tie is rejected). It is a pure function over signed events, shown in the dashboard with the voter's own ballot.
**Limits.** No relaying, history sync or store-and-forward: a member who was offline misses events, so two nodes can show different tallies until they have seen the same ballots, and a ballot cast while you were offline is not counted for you. Governance is advisory: results are verifiable but nothing enforces them, and only the owner can change membership; there is no delegation, weighting, anonymity or ballot secrecy (voters are identified). The owner is a trusted party for membership and can silence a community by removing everyone. Roster and electorate trust each node's own view, and a malicious owner can show different rosters to different members. Plain messages are signed but not end-to-end encrypted beyond the Noise link to each member; encrypted group messaging (group keys) is not in the spec's feature list and is not built. Community text is rendered as text, never HTML.

## Node operator tools (`src/operator.ts`)
A persistent ban list (SQLite `bans`) loaded into a live set that the libp2p connection gater reads: dials to a banned peer, inbound and outbound encrypted connections from it, and its relay reservations are refused (the peer ID is known only after Noise, so a banned peer can still open a socket briefly). Banning also closes existing connections. Other tools: disconnect, run the retention sweep now, and a snapshot of process memory/load, connection counts (in, out, relayed) and rejected-traffic counters per protocol and reason (reasons that carry error text are collapsed; at most 100 counters). The dashboard "Network Nodes" tab shows these next to storage, relay and NAT status. **Limits.** Local only: the control API is loopback-only, so there is no remote administration and no shared ban lists. Bans are by peer ID, which an attacker can rotate; see the next section for what raises the cost of that. Automatic blocks from reputation use the same gater.

## DIDs, credentials and recovery (`src/did.ts`, `src/credentials.ts`, `src/recovery.ts`, `src/cli-identity.ts`)
**DID.** `did:key:z` + base58btc(`0xed01` || 32-byte Ed25519 key): the same key as the peer ID, so any Ed25519 peer ID maps to a DID and back. `parseDidKey` is strict (only did:key/Ed25519, canonical base58, no path/query/fragment). The DID document (Multikey, one method used for authentication, assertion, invocation and delegation, `alsoKnownAs: frenet-peer://<id>`) is derived from the identifier, so resolution needs no network. `GET /api/identity`, `GET /api/did/resolve?did|peer`.
**Credentials (VC-JWT, W3C VC Data Model 1.1).** Compact JWTs, `alg: EdDSA`, `kid = <iss>#<key>`, no JSON-LD canonicalisation. Credential `{iss, sub, jti, nbf, iat, exp?, vc:{@context,type:[VerifiableCredential,T],credentialSubject}}`; presentation `{iss=holder, jti, nonce, aud?, iat, exp, vp:{verifiableCredential:[jwt]}}`; revocation `{iss, iat, revokes:jti}` with `typ: frenet-revocation+jwt`. Verifiers pin `alg` and `typ`, take the key from the issuer DID (never from sender-controlled data), require canonical base64url and a 64-byte signature, cap sizes (16 KB credential, 96 KB presentation), and reject payloads that mix claim kinds, so one kind of token cannot be replayed as another. A presentation verifies only against the verifier's own `nonce` (and `aud` if present), every embedded credential must verify, and each must be about the presenter. Credentials are issued/held in SQLite (`credentials`), revocations in `revocations`; a revocation only ever affects credentials of the DID that signed it. API: `GET /api/credentials`, `POST /api/credentials/issue|verify|import|delete|revoke|revocations`, `POST /api/presentations/create|verify`.
**Recovery.** The account is the key, so recovery restores the same key (a new key would be a different identity to everyone who knows you). (1) *Backup*: `frenet-backup:v1:` + base64url JSON `{kdf:scrypt N=2^17 r=8 p=1, salt, nonce, AES-256-GCM ct, peer}`; the header is the GCM AAD, N is capped at 2^18 when reading (untrusted input), the decrypted key must parse as Ed25519 and match `peer`; passphrase >= 12 chars, NFKC-normalised. (2) *Shares*: Shamir over GF(2^8) (AES polynomial), per-byte random polynomial of degree k-1, x = 1..n (n <= 32); the secret carries a 4-byte SHA-256 trailer so a wrong combination is rejected, each share is `frenet-share:1:k:set:x:data:checksum` (typo detection, random set id so splits are never mixed). `installKey` writes `identity.key` atomically with 0600 and never replaces a different key without `--force` (old key kept as `.replaced-<time>`). These are **CLI-only** (`frenet identity|backup|restore|recovery`) and deliberately absent from the HTTP API.
**Limits.** A did:key cannot be rotated or revoked, so a stolen key cannot be recovered from (no pre-rotation / KERI-style continuity yet). Revocation is pull-only; nothing distributes statements. Credentials are not exchanged over the network by the node (hand the JWT over any channel, e.g. a message). Backup covers the key only: messages, blocks, held credentials and file keys are separate. No dashboard UI yet.

## Content safety (`src/moderation.ts`)
**Why local.** A node serves other people's data and there is no central party who can remove it, so every operator needs their own tools. Nothing here is transmitted, gossiped or scanned automatically.
**Blocklist.** SQLite `content_blocks (kind, target, parent, reason, ts)`, `kind` = `cid` (any block: a file manifest, a site manifest, a chunk), `name` (`label.pub`) or `publisher` (`pub`). `parent` is empty for an entry the operator added, else `<kind>:<target>` of the entry that pulled it in, so `unblock` lifts an entry and exactly what it covered, and an item covered by two entries stays blocked until both are lifted. A copy lives in memory (`Moderation.isBlocked`) so the hot paths never query SQLite. **Cascade** (local data only, never the network, bounded by 5000 items): a site manifest lists file manifests, which list chunks, and each level is read only if this node holds it unencrypted, owns the file (`files` table, which also knows encrypted chunks), or is given the file's key (see **Key-assisted blocking**); a name pulls in the site its record points at; a publisher pulls in all its names and their sites. Then the copies are deleted, `files` rows and name records that pointed at them are dropped, and `contentRouting.cancelReprovide` withdraws the advertisement.
**Enforcement points.** `Blocks.putLocal` (no storing or publishing blocked bytes), `Blocks.get` (no fetching; throws `ContentBlocked`), the `/frenet/block/1.0.0` handler (answers nothing), `Blocks.announce`/`reannounce` (never advertised), `Names.publish/resolve/search/list`, the name protocol handler and own re-announce (blocked records are neither stored, served nor announced; a valid-but-blocked record is **not** counted as a bad record, so the sending peer is not penalised), and the gateway, which answers **451** for a blocked site or name before any DHT lookup and for a blocked file inside an otherwise fine site (the API maps `ContentBlocked` to 451 too). A node cannot block itself: the own publisher key is refused.
**Reports.** SQLite `reports`, at most 1000 (full of open reports it refuses; otherwise it drops the oldest resolved ones). A report is `{id, kind, target, category, note<=500, ts, reporter}` signed (Ed25519, domain `frenet-report/v1`, `reporter` = this node's peer ID, so `verifyReport` needs no registry); `status` (`open|blocked|dismissed`) is local workflow and unsigned. Targets are canonicalised (`frenet://`, `frenet-site://`, `frenet-name://` links accepted) and a file link's `#key` is stripped before anything is stored or signed. Notes lose control characters and are rendered as text. Blocking closes every open report about the same target. **Limits.** Exact-hash matching only: a copy with one changed byte, or an encrypted copy under another key, is a different CID. For a file a node holds only as a replica, chunks can be listed only with the file's key; blocked without it, only the manifest is blocked and the orphaned chunks wait out the replica TTL. Blocking does not touch other nodes, and their provider records for the content live up to 48 h. No shared or imported lists, no scanning, no automatic reporting to any authority, and no remote administration (the API is loopback-only). Reports are not sent anywhere: export by copying the JSON.
**Key-assisted blocking.** A file is `frenet://<manifestCid>#<key>`; the manifest block is `nonce | AES-256-GCM ciphertext | tag` with AAD `m` and lists the chunk CIDs, so a replica holder cannot list them without the key. `block`/`reportAndBlock`/`resolve` accept the key in the target link (`keyFromLink`, a 43-character base64url fragment) or as a separate `key` (only for kind `cid`; for any other kind it is an error). `Moderation.closure` passes it to `sealedManifestChunks` (`src/files.ts`) for the **root** manifest only, in memory, and the chunk CIDs it returns join the normal cascade. The key is never stored (not in `content_blocks`, `reports` or the log), never part of a signed report (the `#key` is still stripped by `normalizeTarget`) and never in a response. All validation runs before any state change: a malformed key, or one that does not open the held manifest, throws, and `reportAndBlock` blocks first and files the report second, so a rejected key leaves no half-finished report. The result carries `keyStatus`: `used` (it opened the manifest), `not-needed` (the manifest could already be read: public file or site, own file, or a block that is not a file) or `manifest-not-held` (no manifest here, so the key opened nothing); `null` when no key was given. The manifest must already be in the local store, because nothing is fetched at block time, so once a manifest has been purged without the key its chunks cannot be found again. The dashboard therefore asks for the key (`prompt`) when you click **Block** on an open report, and accepts a pasted link in the report form.
**Not built, on purpose.** *Hotline submission.* The NCMEC CyberTipline API is for registered providers (an application, approval and issued credentials that identify the reporting company), so there is nothing a self-hosted node could call; INHOPE member hotlines take public reports through their own national sites, and which one applies depends on where the operator is. The README and dashboard point to inhope.org, and the signed report is what an operator hands over. *Similarity matching.* Perceptual hash lists such as PhotoDNA are licensed to vetted organisations, and a node that fetched and stored material in order to compare it would be handling it, which is for each operator to decide with legal advice. A stub that looked like reporting or scanning but did neither reliably would give false assurance, so matching stays exact-hash and local.

## Retention
Own blocks are pinned (until deleted or per-file TTL). Replicas fetched from peers expire after `--replica-ttl-days`. Expired blocks are never served and are swept every 10 min and at startup. `--quota-mb` bounds local bytes; over-quota adds fail and roll back, over-quota replicas are served but not cached. Local delete removes manifest + unshared chunks and vacuums the DB; copies on other peers are outside our control.

## Local API (127.0.0.1)
`GET /api/status|peers|messages|events(SSE)|blocks/<cid>|files|names|names/resolve|search|identity|did/resolve|credentials|operator|moderation|communities|communities/messages|communities/proposals`, `POST /api/send|dial|blocks|files|files/get|files/delete|sites|call/signal|credentials/issue|credentials/verify|credentials/import|credentials/delete|credentials/revoke|credentials/revocations|presentations/create|presentations/verify|operator/ban|operator/unban|operator/disconnect|operator/sweep|operator/reannounce|moderation/report|moderation/resolve|moderation/block|moderation/unblock|communities|communities/members|communities/join|communities/leave|communities/post|communities/propose|communities/vote` (base64 `data`). SSE events: `peer|message|dropped|signal|community|group`. Foreign `Host` headers (DNS rebinding) and cross-origin POSTs are rejected; JSON content-type required; strict CSP on static files.

## Known limits
- NAT traversal is best-effort, not guaranteed. Layers, in order: UPnP port mapping (router permitting) -> AutoNAT reachability detection -> circuit-relay v2 reservation on `--relay` peers (or relays discovered among connected peers) -> DCUtR hole punching to upgrade relayed links to direct. Symmetric NATs / CGNAT may stay relay-only.
- Relayed connections are limited (a relay we run allows 2 min / 2 MiB per connection). Messaging and block fetch are allowed over them; large files may need the direct upgrade to succeed. Relays are not a privacy layer: they see peer IDs and traffic volume, but not content (Noise is end-to-end), and `remotePeer` is still the authenticated peer, never the relay.
- Running a relay (`--relay-server`) donates bandwidth (capped at 64 reservations). There is no relay discovery service, and reputation is local only: you must supply relay addresses you trust to be available.
- Firewalls are not modified.
- Messages to offline peers fail; no store-and-forward.

## QUIC (`src/node.ts`)
`@chainsafe/libp2p-quic` (a native Rust/quinn binding) is added next to TCP. Default listen addresses are `/ip4/0.0.0.0/tcp/0` and `/ip4/0.0.0.0/udp/0/quic-v1`; passing `--listen` replaces both, so list QUIC addresses yourself, and `--no-quic` removes the transport. QUIC does its own TLS 1.3 handshake bound to the libp2p identity and multiplexes natively (no Noise or yamux layer). The same connection gater (bans, reputation blocks, proof-of-work, subnet limit) runs for QUIC. **Limits.** UDP may be blocked or throttled by firewalls; AutoNAT/DCUtR/UPnP behaviour for UDP was not tested; UPnP maps TCP ports only, so a NATed node should announce a forwarded UDP port (`--announce`); the transport is third-party native code and belongs in the audit scope.

## Reputation, Sybil resistance and detection (`src/sybil.ts`, `src/reputation.ts`)
**Threat.** A peer ID is free, so one attacker can present thousands. The defences below make that costly or visible; none makes it impossible, and none works without honest nodes being the majority of what you connect to.
**Identity proof-of-work.** A key has `identityWorkBits` = leading zero bits of `sha256("frenet-pow/v1\n" || publicKey)`. With `--min-identity-bits N` the gater refuses inbound and outbound connections to peers below N (peer IDs whose key cannot be inspected also fail). `frenet identity mine --bits N` grinds a *new* identity (about 2^N tries, N=20 is about a minute on a laptop; max 32). Bootstrap and relay peers you configure are exempt. Off by default (0): turning it on partitions you from nodes that did not mine, so it is only useful once the network agrees on a value. Existing identities cannot be upgraded (the key is the identity).
**Network diversity.** `--max-peers-per-subnet` (default 8) caps *distinct inbound peers* per IPv4 /24 or IPv6 /48; one peer reconnecting is not counted twice. Loopback, private, link-local and relayed addresses are exempt (the relay, not the peer, owns that address), so a relay hides a cluster from this rule. Separately, six or more distinct identities seen from one range within an hour are flagged as a cluster (penalty -15 each, once).
**Reputation.** Each verified-bad act is a negative event against the peer that did it: bad signature -25, corrupt block (does not hash to its CID) -40, forged or keyword-stuffed name record -25, oversize -10, malformed -8, replay -6, rate-limit hit -4, non-owner roster -10, sybil cluster -15. Valid message, block or record: +0.5 to +1, capped at +50. Scores halve every 24 h. At -50 the peer is blocked (connection refused, existing connections closed, relay reservations refused) for 1 h, doubling per repeat up to 7 d; after a block the score restarts at -25. Operator-configured bootstrap/relay peers are scored but never auto-blocked. State is persisted (`reputation` table, at most 10,000 peers, blocked peers are never evicted). `GET /api/reputation`, `POST /api/reputation/reset`, the operator snapshot, `--no-auto-ban` to score without blocking.
**What counts as detection.** Only things this node can prove itself: signatures, hashes, schema, rate. Providers that are merely offline or hold an expired block are not penalised. Not detected: eclipse attacks, equivocation by a community owner showing different rosters to different members, selective withholding, slow or low-rate abuse below the limits, and colluding peers that stay individually well-behaved.
**Limits.** Local only: nothing is gossiped, so there is no shared blocklist, and a peer that rotates its ID starts fresh (proof-of-work and the subnet limit are what make that costly). Scores are not used to rank search results or choose relays yet. Thresholds are untuned guesses and were not validated against real network traffic. Legitimate nodes sharing a hosting range can be flagged as a cluster.

## Secure software updates (`src/updates.ts`, `src/cli-update.ts`)
TUF-style, verification side only. **Trust roots**: `{threshold, keys[]}` of release `did:key`s, read from `<data>/update-roots.json` or `--roots FILE`; none are built in and with none configured everything is refused. **Manifest**: `{v:1, product:'frenet', channel, version, seq, created, expires, artifacts:[{name,size,sha256}], notes?}`. **Envelope**: `{payload: base64url(manifest JSON), signatures:[{keyid, sig}]}`, each signature is Ed25519 over `"frenet-update/v1\n" + payload` (the exact string, so no canonicalisation ambiguity). Verification order: size caps, canonical base64url, at least `threshold` *distinct* trusted keys with valid signatures (duplicates, unknown keys and bad signatures are ignored), *then* parse and validate the manifest (product, channel, strict semver, validity window <= 90 days, not dated in the future, artifact names `[A-Za-z0-9_][A-Za-z0-9._-]*` so they cannot traverse paths, lowercase-hex SHA-256), not expired (freeze attack), `seq` not below the highest accepted for the channel (rollback; equal seq must be the same version), version not below the running one (downgrade). Artifact bytes are then checked for size and SHA-256 (`verifyArtifact`).
CLI: `frenet update keygen | manifest | sign | verify`. `verify ... --accept` records the seq after every listed artifact verified. Sign on an offline machine; each signer runs `sign` on the previous output.
**Limits.** No downloader or installer: the node never replaces itself, and delivering bytes (HTTPS, a FRENET block, a USB stick) and installing them are outside this code. Roots are pinned by the operator; there is no root rotation or revocation, so compromise of `threshold` release keys is a full compromise. No reproducible-build or transparency-log check ties a signed hash to source. npm dependencies (libp2p, the QUIC native module) are covered only by `npm audit` in CI, not by this mechanism.
